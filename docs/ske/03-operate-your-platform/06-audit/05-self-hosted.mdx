On a self-hosted cluster, you need to turn on the Kubernetes audit log
yourself, and configure where it is saved. This page shows how to change the
API server configuration to write the audit log, and how to count the users of
your platform from the audit log file, and from
[Loki](https://grafana.com/docs/loki/latest/) and Grafana. If you keep your
logs in another log system, the audit events are the same, and only the
queries change.

Each create, update and delete of a resource request carries the
[audit annotation](/ske/operations/audit/requester#audit-log)
`attribution.platform.syntasso.io/last-changed-by`, set to the user who made
the change.

## Turning on the audit log

The API server writes the audit log when you give it an audit policy and a
log path. See
[Auditing](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/)
in the Kubernetes documentation.

SKE adds the audit annotation to each create, update and delete of a resource
request, and the `Metadata` level is enough to record it:

```yaml title="audit-policy.yaml"
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages:
  - RequestReceived
rules:
  - level: Metadata
    verbs: ["create", "update", "patch", "delete"]
```

The audit annotation is only on the later stages of each request, so leaving
out the `RequestReceived` stage drops events that never name a user.

To turn the audit log on, start the API server with these flags:

```bash
--audit-policy-file=/etc/kubernetes/audit-policy.yaml
--audit-log-path=/var/log/kubernetes/audit/audit.log
--audit-log-maxage=7
--audit-log-maxbackup=10
--audit-log-maxsize=100
```

If the API server runs as a static Pod, for example on a cluster created with
kubeadm, also mount the policy file and the log directory into the Pod. See
[Log backend](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/#log-backend)
for an example.

## Finding the logs

The API server writes each audit event as one line of JSON to the
`--audit-log-path` file on each control plane node. The user is in
`annotations["attribution.platform.syntasso.io/last-changed-by"]`.

You can count users from the file itself, or send the file to your log system
with the log shipper you already run, for example to Loki if you use Grafana.

The example Loki queries on this page select the audit log with
`{job="kube-apiserver-audit"}`. Change the selector to match the labels your
log shipper sets.

## Setting log retention {#retention}

You can only see activity and count your platform users while their events are
still in the audit log file or in your log system. To count the users who used
your platform over the last year, you need to keep a year of logs.

The API server rotates its own file with `--audit-log-maxage`,
`--audit-log-maxbackup` and `--audit-log-maxsize`. If you count users from the
file, these flags set how far back you can count. If you send the file to
Loki, the file only needs to last until your log shipper reads it.

If you use Loki, configure its retention, for example with these settings:

```yaml
compactor:
  retention_enabled: true
  delete_request_store: <OBJECT_STORE>
limits_config:
  retention_period: 8760h
  max_query_length: 8761h
```

- `retention_period` is how long Loki keeps logs. Loki only deletes logs when
  `retention_enabled` is `true`, and it then needs `delete_request_store` set
  to the object store it uses, such as `s3` or `gcs`. See
  [Log retention](https://grafana.com/docs/loki/latest/operations/storage/retention/)
  in the Loki documentation.
- `max_query_length` is the longest time range one query can cover. It is 30
  days and 1 hour by default, so a count over a longer range fails until you
  raise it.

Loki stores every log it keeps, so a longer retention costs more storage.

## Counting platform users {#unique-users}

With the audit log turned on, you can count platform users from the audit log
file or from your log system. This page uses Loki as the example log system,
because it is a common choice for logs that you view in Grafana.

### From the audit log file

On a control plane node, run this to count the users since `<START_DATE>`,
for example `2026-11-01`. It reads the current file and the rotated ones, and
needs [jq](https://jqlang.org/):

```shell-session {10}
user@control-plane:~$ sudo cat /var/log/kubernetes/audit/audit*.log \
  | jq -r --arg key attribution.platform.syntasso.io/last-changed-by '
      select(.annotations[$key] != null
        and .stage == "ResponseComplete"
        and .responseStatus.code < 400
        and (.requestURI | contains("dryRun") | not)
        and .requestReceivedTimestamp >= "<START_DATE>")
      | .annotations[$key]' \
  | sort -u | wc -l
4
```

This `select` keeps the changes to resource requests that succeeded. It drops
the changes Kubernetes rejected and any dry runs, such as the ones
`kubectl diff` sends, which also carry the audit annotation.

Each control plane node writes its own file. On a cluster with more than one
control plane node, copy the files from all of them and run the command on
all the files together, or the count misses users who only reached another
node.

#### Other useful audit log file commands

How many changes each user made:

```shell-session {10-13}
user@control-plane:~$ sudo cat /var/log/kubernetes/audit/audit*.log \
  | jq -r --arg key attribution.platform.syntasso.io/last-changed-by '
      select(.annotations[$key] != null
        and .stage == "ResponseComplete"
        and .responseStatus.code < 400
        and (.requestURI | contains("dryRun") | not)
        and .requestReceivedTimestamp >= "<START_DATE>")
      | .annotations[$key]' \
  | sort | uniq -c | sort -rn
      3 alice@example.com
      2 bob@example.com
      1 kubernetes-admin
      1 carol@example.com
```

Who created, updated and deleted a request:

```shell-session {12-13}
user@control-plane:~$ sudo cat /var/log/kubernetes/audit/audit*.log \
  | jq -r --arg key attribution.platform.syntasso.io/last-changed-by '
      select(.annotations[$key] != null
        and .stage == "ResponseComplete"
        and .responseStatus.code < 400
        and (.requestURI | contains("dryRun") | not)
        and .objectRef.namespace == "<NAMESPACE>"
        and .objectRef.name == "<REQUEST_NAME>")
      | [.requestReceivedTimestamp, .annotations[$key],
         .verb, .objectRef.resource] | @tsv' \
  | sort -r
2026-11-17T09:04:37.366545Z     alice@example.com       patch   redis
2026-11-17T09:04:31.770364Z     alice@example.com       create  redis
```

### Using Grafana Explore

Loki has no interface of its own, so you run Loki queries in Grafana,
through its
[Loki data source](https://grafana.com/docs/grafana/latest/datasources/loki/).

1. In Grafana, open **Explore** and choose your Loki data source.
1. Choose the time range to count over.
1. Select the query name **A**, and rename it to `users`. Grafana names the
   result column after the query, as `Value #users`.
1. Set the query type to **Instant**, and run this query:

```
count(sum by (user) (count_over_time(
  {job="kube-apiserver-audit"}
    | json
      user="annotations[\"attribution.platform.syntasso.io/last-changed-by\"]",
      stage="stage",
      code="responseStatus.code",
      uri="requestURI"
    | user != "" and stage = "ResponseComplete"
      and code < 400 and uri !~ ".*dryRun.*"
  [$__range]
)))
```

The `json` step reads the user and the fields the filter needs from each
event. The filter keeps the changes to resource requests that succeeded. It
drops the changes Kubernetes rejected and any dry runs, such as the ones
`kubectl diff` sends, which also carry the audit annotation.

`verb` is the Kubernetes API verb, which depends on how the tool sends the
change. Most tools, such as `kubectl apply`, `kubectl edit`, Flux and Argo CD,
send changes to an existing request as `patch`. Tools that send the whole
request, such as `kubectl replace`, show as `update`.

## Known limitations

- **Counts only go back as far as your [retention](#retention)**, and as far
  as `max_query_length` allows.
- **The recorded user is only as specific as the way users log in.** If users
  share one credential, such as the `kubernetes-admin` certificate that
  kubeadm creates, the audit log records the same user for all of them. Run
  `kubectl auth whoami -o yaml` to see which fields your cluster gives you,
  and set [`userInfoField`](/ske/operations/audit/requester#user-info-field)
  to a field that is different for each user.
- **Some changes have no user.** For example, changes made while the SKE
  Platform Manager is unreachable. See
  [What is not recorded](/ske/operations/audit/requester#what-is-not-recorded).
- **Deletes through GitOps name the GitOps tool's service account**, not a
  person, so a count of users includes it.
