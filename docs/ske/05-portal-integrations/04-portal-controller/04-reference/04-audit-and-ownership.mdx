When you use GitOps, a GitOps tool such as Argo CD applies each request to
Kubernetes with its own ServiceAccount, so Kubernetes cannot see which user
made the change. SKE records that user on the request itself, in three
`kratix.io` annotations. The SKE portal integrations for Backstage and Cortex
both write them.

## Requirements

- `@syntasso/plugin-ske-backend` `<RELEASE_VERSION>` or later (for Backstage).
- Portal Controller `<RELEASE_VERSION>` or later.

## Annotations

| Annotation | Value |
|---|---|
| `kratix.io/last-changed-by` | In Backstage, the value `userIdentifierQuery` finds on the person's User entity. In Cortex, the person's email address |
| `kratix.io/last-change-action` | `create` or `update` |
| `kratix.io/last-changed-via` | The portal type: `backstage` or `cortex` |

```yaml
apiVersion: marketplace.kratix.io/v1alpha1
kind: Jenkins
metadata:
  name: my-jenkins
  namespace: default
  annotations:
    kratix.io/last-changed-by: alice@example.com
    kratix.io/last-change-action: update
    kratix.io/last-changed-via: backstage
```

Every create or update from a portal replaces all three, so they describe
the latest change, not the first one.

## Configuration

### Backstage

Set `userIdentifierQuery` in the `config` of each `type: backstage` entry in
`portals[]`:

```yaml
apiVersion: platform.syntasso.io/v1alpha1
kind: SKEIntegration
metadata:
  name: portal-controller
spec:
  type: portal-controller
  version: <RELEASE_VERSION>
  portals:
    - name: prod
      type: backstage
      config:
        # highlight-next-line
        userIdentifierQuery: user.spec.profile.email
```

`userIdentifierQuery` is a path into the catalog entity of the signed-in
user. It starts with `user.`, which stands for that entity, so
`user.spec.profile.email` reads the entity's `spec.profile.email`.

Every Backstage sign-in provider stores the user's details in a different place
on the User entity. SKE cannot know where yours keeps them, so
`userIdentifierQuery` tells it where to look.

The SKE backend plugin reads the value from the signed-in user's entity
when the request is submitted. A Template cannot set it.

`userIdentifierQuery` is optional. Without it, requests from that portal
get no annotations.

The request will fail when `userIdentifierQuery` is set in the following
situations:

- the person has no User entity in the catalog, for example a guest
- the query finds no value, or the value is not text
- the query does not start with `user.`

:::info Upgrading the Backstage backend plugin

You can upgrade the backend plugin and the Portal Controller in either order.
However, only set `userIdentifierQuery` after you upgrade the backend plugin.
An older plugin refuses every request from a Template that passes it.

:::

### Cortex

Cortex needs no specific configuration. The create and update workflows that
the Portal Controller generates always write the annotations, using the email
address of the person who ran the workflow.

:::info Upgrading from older Portal Controllers

Cortex used to write `cortex.io/initiated-by` and `cortex.io/initiated-action`.
It now writes the `kratix.io` annotations, and for one release it still reads
the old ones, so requests made before the upgrade keep their owner in Cortex.

:::

## Requiring the annotation from a GitOps tool {#require-last-changed-by}

By default, SKE does not check that a request says who made it. You can make
SKE reject the requests your GitOps tool applies when they don't carry
`kratix.io/last-changed-by`. Use this when every request in git should come
from a portal.

This needs SKE Operator `<RELEASE_VERSION>` or later, and an SKE version that
includes the SKE Platform Manager `<RELEASE_VERSION>` or later.

### Configuration

List the ServiceAccounts of your GitOps tool in
`spec.attribution.requireAnnotationsFrom.serviceAccounts` on the
[Kratix resource](/ske/reference/ske-operator#kratix-crd):

```yaml
apiVersion: platform.syntasso.io/v1alpha1
kind: Kratix
metadata:
  name: my-kratix
spec:
  # highlight-start
  attribution:
    requireAnnotationsFrom:
      serviceAccounts:
        - namespace: argocd
          name: argocd-application-controller
  # highlight-end
```

When you change this list, the SKE Operator restarts the SKE Platform Manager
so it picks up the change.

For example, Argo CD applies resources with the
`argocd-application-controller` ServiceAccount, and Flux with the
`kustomize-controller` ServiceAccount. Check the namespace and name in your
own installation.

Without any ServiceAccounts listed, nothing is checked.

#### Without the SKE Operator

If you install SKE from the SKE distribution manifest instead of with the SKE
Operator, create the ConfigMap the SKE Operator would write:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ske-platform-manager-config
  namespace: kratix-platform-system
data:
  config: |
    attribution:
      requireAnnotationsFrom:
        serviceAccounts:
          - namespace: argocd
            name: argocd-application-controller
```

The SKE Platform Manager only reads this ConfigMap when it starts, so restart
it after you create or change the ConfigMap:

```bash
kubectl -n kratix-platform-system rollout restart deployment/ske-platform-manager
```

### What is checked

The SKE Platform Manager rejects a create or update of a resource request when
both are true:

- it comes from one of the listed ServiceAccounts
- `kratix.io/last-changed-by` is missing or empty

The error says which request needs the annotation, and why:

```
admission webhook "attribution.platform.syntasso.io" denied the request:
Jenkins default/my-jenkins needs the kratix.io/last-changed-by annotation, set
to the person who made the change. SKE requires it on resource requests applied
by service account argocd/argocd-application-controller.
```

The check does not affect:

- requests from any other user or ServiceAccount
- deletes, because a GitOps delete removes the file from git, so it cannot
  carry the annotation
- resources that are not resource requests

### Limitations

- **The check never blocks Kratix.** If the SKE Platform Manager is not
  running, Kubernetes accepts the request without checking it.
- **New Promises are not checked straight away.** For a few seconds after you
  install a Promise, its requests are accepted without the check.
- **Only the annotation's presence is checked.** SKE does not check that the
  value is the person who made the change. For example, if someone edits a
  request's file in git by hand and keeps the old annotation, the request is
  accepted.

## Deletes and usage outside of a portal

A delete through GitOps removes the request's file from git, so nothing
records who deleted it.

A request created outside a portal, for example with `kubectl`, has no
annotations unless you add them.
