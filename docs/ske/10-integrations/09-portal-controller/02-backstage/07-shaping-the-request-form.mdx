The Portal Controller turns a Promise's API into a Backstage `Template`, and that Template is the
form your developers fill in. Most of what you want the form to do, you write into the CRD in
`spec.api`: required fields, dropdowns, defaults, validation, fields nobody can change later, and
fields that only appear once something else is chosen.

For the rest, bind the Promise to a [`PortalCustomization`](../customization) and patch the
Template the generator produced.

The examples below are fragments of one `postgresql` Promise. Each sits under `spec.api`, in
`spec.versions[0].schema.openAPIV3Schema.properties.spec`.

## What your Promise API controls

### Required fields

List the property in `required` on the object that holds it. Backstage marks it with an asterisk
and will not move on to the next page until it has a value.

```yaml
spec:
  type: object
  required:
    - size
  properties:
    size:
      type: string
```

### Dropdowns and defaults

`enum` gives the developer a dropdown, and `default` preselects one of the values.

```yaml
size:
  type: string
  title: Instance size
  description: How much CPU and memory the database gets.
  enum: [small, medium, large]
  default: small
```

`title` is the field label and `description` is the helper text underneath it. Set a `title` on
nested properties too. Without one the generator builds the label out of the parent's title, so a
`dayOfWeek` inside `maintenance` reaches the form as `Maintenance window.DayOfWeek`.

### Fields nobody can change after creation

Freeze a field with a CEL validation rule on the CRD:

```yaml
region:
  type: string
  title: Region
  description: Region the database is created in.
  enum: [eu-west-1, us-east-1]
  x-kubernetes-validations:
    - rule: self == oldSelf
      message: region is immutable
```

The API server now rejects any update that changes `region`, and the generator marks the property
so the SKE frontend renders it read-only on the
[Manage tab](./frontend-plugin#resource-manage). It stays editable on the create form, where
there is nothing yet to preserve.

Only `self == oldSelf` freezes the whole field, in either operand order. A narrower rule such as
`self.tier == oldSelf.tier` still holds at the API server, but it does not lock the field in the
form.

### Either/or configuration

`oneOf` lets a developer configure one of several things rather than all of them. Each option
lists the properties it needs, and Backstage renders a radio button per option, showing only the
fields that belong to the option selected.

```yaml
backups:
  type: object
  title: Backups
  description: Where backups are shipped.
  oneOf:
    - required: [s3]
    - required: [gcs]
  properties:
    retentionDays:
      type: integer
      title: Retention (days)
      default: 30
    s3:
      type: object
      title: Amazon S3
      properties:
        bucket:
          type: string
          title: Bucket
        roleArn:
          type: string
          title: Role ARN
    gcs:
      type: object
      title: Google Cloud Storage
      properties:
        bucket:
          type: string
          title: Bucket
        serviceAccount:
          type: string
          title: Service account
```

Backstage labels each radio button after the property its option requires, which is where "S3"
and "Gcs" come from. A property no option requires, like `retentionDays`, is shared and appears
whichever option is selected.

Give every option at least one property in `required`. An option without one is an error, and the
Promise fails to sync. The developer has to pick an option, so the field itself becomes required.

### Validation

Backstage checks `pattern`, the length keywords and the range keywords in the browser, so the
developer sees the problem before they submit.

```yaml
teamEmail:
  type: string
  title: Team email
  description: Who to page when this database misbehaves.
  pattern: '^[^@]+@example\.com$'
  minLength: 5
  maxLength: 64
replicas:
  type: integer
  title: Replicas
  minimum: 1
  maximum: 5
```

The generator appends `Must match regular expression '<pattern>'` to the description of any
property that has a `pattern`. Backstage turns anything in a description that looks like a URL or
an email address into a link, so a pattern containing either comes out badly:

<figure className="diagram">

  <figcaption>Part of <code>^[^@]+@example\.com$</code> has been linkified, leaving the pattern hard to read</figcaption>

For anything longer than a simple pattern, replace this with a
[validation message of your own](#better-validation-messages).

### Lists and nested objects

An `array` renders as a list the developer adds items to. A nested `object` renders as a group of
fields under its own heading.

```yaml
extensions:
  type: array
  title: Extensions
  description: Postgres extensions to enable.
  maxItems: 5
  items:
    type: string
maintenance:
  type: object
  title: Maintenance window
  properties:
    dayOfWeek:
      type: string
      title: Day of week
      enum: [sunday, monday, tuesday]
      default: sunday
    hourUTC:
      type: integer
      title: Hour (UTC)
      minimum: 0
      maximum: 23
      default: 2
```

### How the form is paged

The generator currently gives each top-level property of `spec` a page of its own, ordered by
property name rather than by title. For the Promise above, that is a ten-page wizard in an order
nobody chose, where "Instance size" turns up eighth because its property is called `size`:

<figure className="diagram">
  <img
    className="fullwidth"
    src={FormPages}
    alt="A Backstage request form with eleven numbered steps: Instance Metadata, Backups, Dedicated node, Extensions, Maintenance window, Region, Replicas, Instance size, Storage (GB), Team email and Review"
  />
  <figcaption>One page per top-level <code>spec</code> property, ordered by property name</figcaption>
</figure>

A single page suits most Promises better, and is becoming the default. Until it does, you can
[collapse the pages yourself](#one-page-in-the-order-you-choose). When the default changes, a page
per property remains available for the Promises that want it.

### Reference

| CRD schema | Effect on the form |
|---|---|
| `title` | Field label. Nested properties without one are prefixed with the parent's title |
| `description` | Helper text below the field |
| `required` | Field is mandatory and marked with an asterisk |
| `default` | Field is prefilled with the value |
| `enum` | Dropdown of the listed values |
| `pattern`, `minLength`, `maxLength` | String validation. The pattern is also appended to the description |
| `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf` | Numeric validation |
| `format` | Passed through to Backstage, for example `email` |
| `type: array`, `minItems`, `maxItems` | A list the developer adds items to |
| `type: object` with `properties` | A group of nested fields |
| `oneOf` with `required` per option | Radio buttons showing only the selected option's fields |
| `x-kubernetes-validations` with `self == oldSelf` | Read-only on the Manage tab, editable on create |

## Changing what the generator produced

A `PortalCustomization` runs after the Template is generated and patches it in place. Reach for
one when what you want belongs to the Template rather than to your API, such as layout and
wording, or when Backstage can do something your CRD has no way to ask for.

Each example below is a single [Portal Patch](../portal-patch/intro) recipe, one entry in the
`args` of the profile's container. [Customization](../customization) covers writing the profile
and binding a Promise to it. The Template only exists on the promise lane, so every recipe here
belongs in `spec.promise.configure`.

### Introduce the resource on its form

By default a request form opens straight onto its fields, with nothing to say what the resource
is. A `description` on a page of the Template's `spec.parameters` fills that gap: Backstage
renders it as Markdown above that page's fields, both when the resource is requested and when it
is updated.

```yaml
target:
  kind: Template
  list:
    path: spec.parameters
    key: title
    value: "Postgresql Instance Metadata"
patch:
  description: |
    ## What this template creates

    A managed database for your service, backed up nightly and reachable only
    from inside the cluster.

    - One database instance, sized for the load you expect
    - A connection secret published alongside your component
    - Nightly backups, kept for 30 days

    **Before you start**, check [choosing a driver](https://example.com/docs).
```

### One page, in the order you choose

`singleSpecPage` folds the per-property pages into one page called "Specification" and leaves the
instance metadata page alone:

```yaml
target:
  kind: Template
op: singleSpecPage
```

There is also a portal-wide
[`--single-spec-page` flag](../installation#portal-wide-generate-flags), which does the same for
every Promise on the portal.

On a single page, `ui:order` sets the order the fields appear in:

```yaml
target:
  kind: Template
  list:
    path: spec.parameters
    key: title
    value: Specification
patch:
  properties:
    spec:
      ui:order:
        [
          size,
          storageGB,
          dedicatedNode,
          region,
          replicas,
          teamEmail,
          backups,
          maintenance,
          extensions,
        ]
```

:::warning
`ui:order` has to account for every property on the page. Miss one and Backstage replaces the
form with `uiSchema order list does not contain properties '<name>'` and a dump of the raw schema.
Either name them all, or end the list with `"*"` to catch whatever you did not name:

```yaml
ui:order: [size, region, "*"]
```
:::

### Show a field only for certain choices

Storage size is only worth asking about on a large instance. To hide `storageGB` until the
developer picks `large`, take it out of `properties` and describe it in a `dependencies` block
instead:

```yaml
target:
  kind: Template
  list:
    path: spec.parameters
    key: title
    value: Specification
patch:
  properties:
    spec:
      properties:
        storageGB: null
        dedicatedNode: null
      dependencies:
        size:
          oneOf:
            - properties:
                size:
                  enum: [small]
            - properties:
                size:
                  enum: [medium]
            - properties:
                size:
                  enum: [large]
                storageGB:
                  type: integer
                  title: Storage (GB)
                  description: Provisioned storage. Only configurable on large instances.
                  minimum: 100
                  maximum: 2000
                dedicatedNode:
                  type: boolean
                  title: Dedicated node
                  description: Run this instance on a node of its own.
              required: [storageGB]
```

Setting `storageGB` and `dedicatedNode` to `null` takes them off the form. The `dependencies`
block is keyed on `size`, the field whose value decides what appears, and gives it one branch per
value. The `large` branch puts both fields back and makes `storageGB` mandatory, while `small`
and `medium` add nothing, so both fields stay hidden.

Every value needs a branch, even the ones that add nothing. Miss one and the form refuses to
submit with `'Specification' must match exactly one schema in oneOf`, which tells a developer
nothing they can act on.

The fields still have to exist on your CRD. This recipe only changes when they are visible, and
the API server strips anything the CRD does not declare. Leave both names in `ui:order` too: a
name matching nothing is ignored, and it puts the revealed fields where you want them instead of
at the end of the page.

  <img
    className="fullwidth"
    src={FormConditional}
    alt="The specification page with Instance size set to large, revealing a required Storage (GB) field and a Dedicated node checkbox directly below it"
  />
  <figcaption>Picking <code>large</code> reveals Storage (GB) and Dedicated node. Picking <code>small</code> or <code>medium</code> hides them again</figcaption>
</figure>

:::warning A hidden field still sends its value
Backstage does not clear a value when the field that revealed it disappears. Pick `large`, type a
storage size, change back to `small`, and the request carries both `size: small` and the storage
size you typed.

Hiding a field is a convenience, not a constraint. Where the combination genuinely matters, rule
it out on the CRD so the API server rejects it:

```yaml
spec:
  type: object
  x-kubernetes-validations:
    - rule: "self.size == 'large' || !has(self.storageGB)"
      message: storageGB may only be set when size is large
```
:::

### Better validation messages

`errorMessage` replaces what Backstage says when a keyword fails, keyed by the keyword that
failed. Pair it with `ui:help` to tell the developer what you want before they get it wrong, and
trim the description so the raw pattern is no longer in it:

```yaml
target:
  kind: Template
  list:
    path: spec.parameters
    key: title
    value: Specification
patch:
  properties:
    spec:
      properties:
        teamEmail:
          description: Who to page when this database misbehaves.
          ui:help: Use a team alias, not a personal address.
          errorMessage:
            pattern: must be an @example.com address
```

### Change how a field is rendered

Any `ui:` key Backstage understands can be patched onto a property. `ui:widget` picks a different
widget for the same data, so an enum of two values can be radio buttons rather than a dropdown:

```yaml
target:
  kind: Template
  list:
    path: spec.parameters
    key: title
    value: Specification
patch:
  properties:
    spec:
      properties:
        region:
          ui:widget: radio
```

Pick a widget that suits the property's type. One that does not fit, such as `checkboxes` on an
array of free text, renders nothing at all rather than complaining, so open the form after
changing one. Backstage's
[ui:options examples](https://backstage.io/docs/features/software-templates/ui-options-examples/)
list the widgets available.

To narrow one dropdown by what was chosen in another, the SKE frontend ships a
[`ScopedEntityPicker`](./frontend-plugin#scopedentitypicker) that you select the same way, with
`ui:field`.
