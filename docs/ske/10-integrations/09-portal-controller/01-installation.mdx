Install the shared Portal Controller once per platform, then configure Backstage or Cortex
on that installation. At the end of this guide, the controller Deployment and its
`PortalCustomization` CRD are ready. Publishing entities is the next step, not proof of installation.

## Requirements

You need cluster administrator access, `kubectl`, SKE and Syntasso registry credentials.
The examples use Portal Controller `v0.6.1`.

| Component | Requirement | Needed for |
|---|---|---|
| SKE | `v0.59.0` or later | The status format supported by this controller |
| SKE Operator | `v0.34.0` or later | Operator-managed deployment and portal configuration |
| Portal Controller | `v0.6.1` | The examples and features documented here |
| `@syntasso/plugin-ske-backend` | `v0.24.0` or later | Backstage request actions and namespace resolution |
| `@syntasso/plugin-ske-frontend` | `v0.22.0` or later | Backstage entity pages and namespace selection |
| Portal Patch | Independently versioned, optional | Declarative customisation; check the [recipe reference](./portal-patch/recipe-reference) |

Install the Backstage packages in Backstage.

## Install the Portal Controller

The [SKE Operator](../../installing-ske/install-with-operator) is the normal installation path.
Use [standalone installation](#installing-without-the-ske-operator) only if the operator
does not manage this integration.

### 1. Check for an existing installation

```bash
kubectl get skeintegrations
kubectl get deployment ske-portal-controller --namespace kratix-platform-system
```

Look for an `SKEIntegration` with `spec.type: portal-controller`. Only one may exist on a
platform. If it already exists, keep its name and `spec.portals` entries; go to
[verification](#verify-the-installation), or [upgrade](#upgrade-the-controller) if needed.

If the Deployment exists without an integration resource, confirm how it is managed before
installing through the operator. Do not install a second controller over a standalone installation.

### 2. Create the integration resource

For a new installation, save this as `portal-controller.yaml`:

```yaml
apiVersion: platform.syntasso.io/v1alpha1
kind: SKEIntegration
metadata:
  name: portal-controller
spec:
  type: portal-controller
  version: v0.6.1
  portals: []
```

```bash
kubectl apply --filename portal-controller.yaml
```

The operator installs the Deployment, CRD, Service Account and RBAC. `portals: []` deliberately
installs no portal instances. Configure your chosen portal after verifying the controller.
Do not apply this empty list to an existing integration: it would remove its portal configuration.

## Verify the installation

For operator-managed installations, replace `<INTEGRATION_NAME>` with the existing resource name:

```bash
kubectl wait --for=condition=IntegrationDeploymentReady \
  skeintegration/<INTEGRATION_NAME> --timeout=180s
kubectl get skeintegration <INTEGRATION_NAME> \
  -o jsonpath='{.status.lastAppliedVersion}{"\n"}'
```

Expect `IntegrationDeploymentReady: True` and the requested applied version, `v0.6.1` in
this example. Check the controller and CRD for either installation method:

```bash
kubectl rollout status deployment/ske-portal-controller \
  --namespace kratix-platform-system --timeout=180s
kubectl wait --for=condition=Established \
  crd/portalcustomizations.platform.syntasso.io --timeout=60s
kubectl get configmap ske-portal-config --namespace kratix-platform-system
```

A ready Deployment is not evidence that a portal's setup or publication has succeeded.
Continue with [Backstage](./backstage/intro) or [Cortex](./cortex/intro), then verify their
generated output. If these checks fail, use [Troubleshoot portal sync](./troubleshooting).

## Upgrade the controller

:::warning Upgrade prerequisites
Upgrade the SKE Operator to `v0.34.0` or later before installing Portal Controller `v0.4.0`
or later. These controller versions read the operator-generated configuration ConfigMap.

Upgrade the Backstage plugins before the controller. Otherwise new Templates can call
actions that the installed backend does not provide; a request may be submitted before
a later Template step fails.

When upgrading SKE to `v0.59.0`, upgrade Portal Controller to at least `v0.4.2` at the same
time. Review [controller releases](/ske/releases/ske-portal-controller),
[SKE releases](../../50-releases/10-ske.mdx) and [Backstage plugin releases](/ske/releases/backstage).
:::

1. Review the release notes for your current and target versions, including plugin and
   recipe compatibility. Upgrade prerequisite components first.
2. In the existing integration's source manifest, change **only** `spec.version` to the target
   released version. Preserve its name, portal entries and deployment settings.
3. Apply that manifest through your normal deployment process. For a locally managed file:

   ```bash
   kubectl apply --filename portal-controller.yaml
   ```

4. Repeat [installation verification](#verify-the-installation). Then verify an existing
   Promise's publication and a test request through the portal-specific guide.

For standalone upgrades, repeat the manifest download and Kustomize apply below using the
target release. Preserve the configuration ConfigMap and your local overlays. Do not apply
the empty bootstrap ConfigMap again.

## Installing without the SKE Operator

This path deploys the released controller manifest directly. It does not install SKE or
its pipeline adapter. Do not use it alongside an operator-managed Portal Controller.

### 1. Check platform dependencies

The SKE installation must already provide the system namespace, pipeline adapter image
configuration and the `syntasso-registry` pull Secret:

```bash
kubectl get namespace kratix-platform-system
kubectl get configmap kratix-platform-pipeline-adapter-config \
  --namespace kratix-platform-system \
  -o jsonpath='{.data.PIPELINE_ADAPTER_IMG}{"\n"}'
kubectl get secret syntasso-registry --namespace kratix-platform-system
```

The ConfigMap must contain a non-empty `PIPELINE_ADAPTER_IMG`. Restore missing dependencies
through your [SKE installation](../../installing-ske/intro) process before proceeding.
The commands above do not print Secret contents.

### 2. Download and configure the released manifest

In a new local directory for this installation, download the manifest:

```bash
mkdir portal-controller-install
cd portal-controller-install
curl --fail --location --output ske-portal-controller.yaml \
  https://syntasso-enterprise-releases.s3.eu-west-2.amazonaws.com/ske-portal-controller/v0.6.1/ske-portal-controller.yaml
```

The manifest contains the CRD, RBAC, Service Account and controller Deployment. It does
not create the namespace or configure the Deployment's private-registry pull credentials.
Save this overlay as `kustomization.yaml` beside the downloaded file:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ske-portal-controller.yaml
patches:
  - target:
      kind: Deployment
      name: ske-portal-controller
    patch: |-
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: ske-portal-controller
      spec:
        template:
          spec:
            imagePullSecrets:
              - name: syntasso-registry
```

### 3. Create the portal configuration

For a **new installation only**, save this as `portal-config.yaml` to bootstrap an empty
configuration. No entities are published until you add a portal instance:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ske-portal-config
  namespace: kratix-platform-system
data:
  connections.yaml: "[]"
```

```bash
kubectl apply --filename portal-config.yaml
```

If this ConfigMap already exists, preserve its entries instead. When adding a portal,
use the entry fields and complete examples in the
[configuration reference](./reference/portal-configuration#configuration-ownership).
Create any referenced Cortex credential Secret through your Secret management process first.

### 4. Deploy and verify

```bash
kubectl apply --kustomize .
```

Repeat the Deployment, CRD and ConfigMap checks under [verification](#verify-the-installation).
Do not run the `SKEIntegration` checks: standalone installations have no integration resource.

## Air-gapped environments

Mirror the images below and configure registry access before installing:

| Image | Needed for |
|---|---|
| `ghcr.io/syntasso/ske-portal-controller:<VERSION>` | The controller and bundled adapter |
| `ghcr.io/syntasso/portal-patch:<VERSION>` | Optional Portal Patch recipes |
| An overridden `adapterConfig.image` | A portal with an adapter override |
| Each `PortalCustomization` container image | Custom configure stages |

The Kratix pipeline adapter image is also required and is part of the SKE installation.
For operator-managed installations, use the operator's
[registry configuration](../../installing-ske/install-with-operator#air-gapped-mirrors).
For standalone installations, add image replacements to your Kustomize overlay for both
the Deployment image and its `PORTAL_ADAPTER_IMG` environment value. The pipeline adapter
ConfigMap must also name a reachable image.

Adapter pull-secret overrides are separate from controller Deployment pull credentials.
See [Adapter reference](./reference/adapter#image-and-workload-overrides).
