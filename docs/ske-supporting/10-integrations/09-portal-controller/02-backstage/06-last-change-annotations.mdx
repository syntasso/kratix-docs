When using GitOps, a request is applied onto Kubernetes through a GitOps tool,
like ArgoCD, using its own ServiceAccount. This prevents Kubernetes from seeing
which user actually created this request. SKE relies on three annotations under
`kratix.io` to keep ownership information. These annotations are written by the
SKE portal integrations for both Backstage and Cortex.

## Requirements

- `@syntasso/plugin-ske-backend` `<RELEASE_VERSION>` or later (for Backstage).
- Portal Controller `<RELEASE_VERSION>` or later.

## The annotations

| Annotation | Value |
|---|---|
| `kratix.io/last-changed-by` | The value `userIdentifierQuery` finds on the person's User entity |
| `kratix.io/last-change-action` | `create` or `update` |
| `kratix.io/last-changed-via` | The portal type: `backstage` or `cortex` |

```yaml
apiVersion: marketplace.kratix.io/v1alpha1
kind: Jenkins
metadata:
  name: my-jenkins
  namespace: default
  annotations:
    kratix.io/last-changed-by: alice@example.com
    kratix.io/last-change-action: update
    kratix.io/last-changed-via: backstage
```

Every create or update from a portal replaces all three, so they describe
the latest change, not the first one.

## Configuration

### Backstage

Set `userIdentifierQuery` in the `config` of each `type: backstage` entry in
`portals[]`:

```yaml
apiVersion: platform.syntasso.io/v1alpha1
kind: SKEIntegration
metadata:
  name: portal-controller
spec:
  type: portal-controller
  version: <RELEASE_VERSION>
  portals:
    - name: prod
      type: backstage
      config:
        # highlight-next-line
        userIdentifierQuery: user.spec.profile.email
```

`userIdentifierQuery` is a path into the catalog entity of the signed-in
user. It starts with `user.`, which stands for that entity, so
`user.spec.profile.email` reads the entity's `spec.profile.email`.

| `userIdentifierQuery` | Records |
|---|---|
| `user.spec.profile.email` | The email address on the User entity |
| `user.metadata.name` | The User entity's name |

The SKE backend plugin reads the value from the signed-in user's entity
when the request is submitted. A Template cannot set it.

`userIdentifierQuery` is optional. Without it, requests from that portal
get no annotations.

When `userIdentifierQuery` is set, the request fails, with a message naming
the query, when:

- the person has no User entity in the catalog, for example a guest
- the query finds no value, or the value is not text
- the query does not start with `user.`

Not every sign-in method fills in every property. For example, GitHub
sign-in does not set `spec.profile.email`. Choose a property that your
sign-in resolver fills in for every user.

::: info Upgrading the Backstage backend plugin

You can upgrade the backend plugin and the Portal Controller in either
order. Set `userIdentifierQuery` only after you upgrade the backend plugin. An
older plugin refuses every request from a Template that passes it.

:::

::: info Upgrading from older Portal Controllers

Cortex used to write `cortex.io/initiated-by` and
  `cortex.io/initiated-action`. It now writes the `kratix.io` annotations,
  and for one release it still reads the old ones, so requests made before
  the upgrade keep their owner in Cortex.


## Deletes and usage outside of a portal

- A delete through GitOps removes the request's file from git, so nothing
  records who deleted it.
- A request created outside a portal, for example with `kubectl`, has no
  annotations unless you add them.
