Audit log on Google GKE

On Google GKE, the Kubernetes API server sends its audit log to Cloud Logging. This page shows where to find the audit log, and how to count the users of your platform, in Observability analytics or in a Grafana dashboard.

Each create, update and delete of a resource request carries the audit annotation attribution.platform.syntasso.io/last-changed-by, set to the user who made the change.

Turning on the audit log​

GKE always writes creates, updates and deletes to the Admin Activity audit log, so there is nothing to turn on. See GKE audit logging in the GKE documentation.

Finding the logs​

GKE writes the Admin Activity audit log to the _Required log bucket of your project, with the log ID cloudaudit.googleapis.com/activity. Each entry is one audit event. GKE turns each audit annotation into a label on the entry, so the user is in the label attribution.platform.syntasso.io/last-changed-by.

Log retention​

You can only see activity and count your platform users if their events are still in the bucket. The _Required bucket keeps logs for 400 days at no charge, and you can't change its retention.

To count the users over more than 400 days, route a copy of the audit log to a log bucket with a longer retention. See Routing and storage overview in the Cloud Logging documentation. Cloud Logging charges for the logs it stores in other buckets. Check the Google Cloud Observability pricing page to find out the relevant price for your scenario.

Counting platform users​

Logs Explorer can filter log entries, but it can't count them. To count your platform users, use Observability analytics, which runs SQL on a log bucket, or Grafana.

Turning on Observability analytics​

warning

You can't undo this upgrade. After the upgrade, entries written before it can take several days to become available to SQL.

Upgrade the _Required bucket to use Observability analytics:

gcloud logging buckets update _Required \
  --project <PROJECT_ID> \
  --location global \
  --enable-analytics

In the Google Cloud console, the Logs storage page shows Open for the _Required bucket once the upgrade is done:

Using Observability analytics​

  1. In the Google Cloud console, go to Logging > Observability analytics.
  2. Choose the time range to count over.
  3. Run this query:
SELECT COUNT(DISTINCT user) AS users
FROM (
  SELECT
    JSON_VALUE(labels['attribution.platform.syntasso.io/last-changed-by']) AS user
  FROM `<PROJECT_ID>.global._Required._AllLogs`
  WHERE log_id = 'cloudaudit.googleapis.com/activity'
    AND JSON_VALUE(resource.labels.cluster_name) = '<CLUSTER_NAME>'
    AND IFNULL(proto_payload.audit_log.status.code, 0) = 0
    AND JSON_VALUE(labels['command.gke.io/dryRun']) IS NULL
)
WHERE user IS NOT NULL

This WHERE keeps the changes to resource requests in your cluster that succeeded. The _Required bucket holds the audit log of every cluster in the project, so the query filters on the cluster name. It drops the changes Kubernetes rejected, which have a status code, and any dry runs, such as the ones kubectl diff sends, which GKE labels with command.gke.io/dryRun.

Other useful Observability analytics queries​

How many changes each user made:

SELECT user, COUNT(*) AS changes
FROM (
  SELECT
    JSON_VALUE(labels['attribution.platform.syntasso.io/last-changed-by']) AS user
  FROM `<PROJECT_ID>.global._Required._AllLogs`
  WHERE log_id = 'cloudaudit.googleapis.com/activity'
    AND JSON_VALUE(resource.labels.cluster_name) = '<CLUSTER_NAME>'
    AND IFNULL(proto_payload.audit_log.status.code, 0) = 0
    AND JSON_VALUE(labels['command.gke.io/dryRun']) IS NULL
)
WHERE user IS NOT NULL
GROUP BY user
ORDER BY changes DESC

Who created, updated and deleted a request:

SELECT timestamp, user, verb, type
FROM (
  SELECT
    timestamp,
    JSON_VALUE(labels['attribution.platform.syntasso.io/last-changed-by']) AS user,
    REGEXP_EXTRACT(proto_payload.audit_log.method_name, r'[^.]+$') AS verb,
    REGEXP_EXTRACT(proto_payload.audit_log.resource_name, r'([^/]+)/[^/]+$') AS type,
    proto_payload.audit_log.resource_name AS resource_name
  FROM `<PROJECT_ID>.global._Required._AllLogs`
  WHERE log_id = 'cloudaudit.googleapis.com/activity'
    AND JSON_VALUE(resource.labels.cluster_name) = '<CLUSTER_NAME>'
    AND IFNULL(proto_payload.audit_log.status.code, 0) = 0
    AND JSON_VALUE(labels['command.gke.io/dryRun']) IS NULL
)
WHERE user IS NOT NULL
  AND REGEXP_CONTAINS(resource_name, r'/namespaces/<NAMESPACE>/[^/]+/<REQUEST_NAME>$')
ORDER BY timestamp DESC

verb is the last part of the entry's method name, which is the Kubernetes API verb. It depends on how the tool sends the change. Most tools, such as kubectl apply, kubectl edit, Flux and Argo CD, send changes to an existing request as patch. Tools that send the whole request, such as kubectl replace, show as update.

Grafana​

Grafana can run the same queries through its Google BigQuery data source, on a BigQuery dataset linked to the _Required bucket. The dashboard below shows the number of unique users, the number of changes, the changes each user made, and the most recent changes. To set it up:

  1. Link the _Required bucket to a BigQuery dataset. See Query a linked BigQuery dataset in the Cloud Logging documentation. For example, with the gcloud CLI:

    gcloud logging links create <DATASET> \
      --project <PROJECT_ID> \
      --bucket _Required \
      --location global

  2. Give Grafana access to the dataset. See Configure the Google BigQuery data source in the Grafana documentation. The identity Grafana uses needs the BigQuery Job User role on the project and read access to <DATASET>. The data source tests its connection and lists projects through the Cloud Resource Manager API, so turn that API on in the project.

  3. Install the Google BigQuery data source plugin, which is not built into Grafana, and add the data source.

  4. Copy the dashboard below, replace <PROJECT_ID>, <DATASET> and <CLUSTER_NAME>, then import it and choose your Google BigQuery data source.

Each query in the dashboard filters with $__timeFilter(timestamp), so it counts over the dashboard's time range. BigQuery charges for the data each query reads, and every panel runs a query each time the dashboard refreshes. Check the BigQuery pricing page to find out the relevant price for your scenario.

Known limitations​

  • Counts only go back as far as your retention.
  • The recorded user is only as specific as the way users log in. On GKE, users usually log in with their Google account, so the audit log records their email. If many users share one service account, the audit log records that service account for all of them. Run kubectl auth whoami -o yaml to see which fields your cluster gives you, and set userInfoField to a field that is different for each user.
  • Some changes have no user. For example, deletes through GitOps. See What is not recorded.
